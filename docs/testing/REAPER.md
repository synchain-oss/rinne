# REAPER 本机宿主烟测

用途：在上 Cubase 之前，先在本机用 REAPER 把「两个插件放进同一条插入链、渲染、存盘重开」这一类能自动化的事跑一遍，早点挡掉明显的退化。它是预检与本机回归，**不替代 Cubase / LUNA**。

- REAPER 的数据**不计入** Cubase 的结论：这里的绿不能当作 Cubase 的绿，日志也与 Cubase 的分开存放。
- REAPER 在 DAW 分级里仍是 Tier 3（见 `docs/daw-tiers.json`），本工具不改分级。
- REAPER 的评估许可只在本机使用；评估期过后按 EULA 须购买许可，本工具不会自动点掉许可提示窗。本工具不进 CI，不挂 gates，不进 ctest。要上 CI 须先向 Cockos 确认许可条款。
- 第一段只测本机构建的 `dev` 风味（段名前缀 D），第二段只测本机构建的探针风味（`build.ps1 -Probe`，段名前缀 P）。都是插件的副本，不测装机版；两种产物不能混用，预检按这一段要的风味核对构建清单与类 ID。

## 测什么（第一段）

当前两个插件是逐位直通的壳，所以第一段只验证「宿主怎么放、怎么渲染都不改一个样本」。场景表是 `tests/reaper/scenarios.json`，每一项的判据都是：渲染结果与同参数的无插件渲染用 `rinne_nulltest compare` 对拍，逐位相同、lag 为 0、前 2 s 的残差为 −inf。

| 场景 | 内容 |
|---|---|
| `null-<模式>-<采样率>-<块长>` | Input 在首、Output 在末；全速离线渲染与 1x 渲染（REAPER 的 1x Offline：按实时速度跑，但对插件报的仍是离线模式，不是在线渲染）；44.1 k / 48 k；块长 64 / 512 / 1024 |
| `device-<采样率>-<块长>` | 读回设备块长与采样率与设定一致；两个插件的 `pdc` 与 `chain_pdc_actual` 都是 0 |
| `mono-offline` | 单声道信号与单声道渲染 |
| `bypass-input` / `bypass-output` / `bypass-both` | 插件旁路 |
| `save-reopen` | 存盘后重开，旁路状态与延迟上报还在，重开后的工程再渲染仍逐位相同 |
| `instances-25` | 一条轨道上反复加减两个插件 25 次，REAPER 不崩，句柄与私有内存的增长有上界 |

反例（`negative` 一栏）必须按预期变红，工具才算可信：

| 反例 | 期望 |
|---|---|
| `neg-offset-1-sample`：渲染结果偏 1 个样本 | FAIL |
| `neg-track-minus-6db`：轨道推子 −6 dB | FAIL |
| `neg-timeout` / `neg-killed`：驱动卡住，超时或到点被结束 | INCOMPLETE，原因分别是超时、到点被结束，进程已结束，gui 锁已释放（gui 锁等不到、卡对话框、REAPER 自己退出都不算验证过） |
| `neg-user-testing`：放上 `USER_TESTING` 标记 | SKIPPED，一次 REAPER 都不启动 |
| `neg-sentinel-missing`：配置目录缺哨兵文件 | 拒绝启动 |
| `neg-default-dir`：配置目录指向 REAPER 的默认资源目录 | 拒绝启动 |

## 结局词汇

每个场景一个结局：`PASS`、`FAIL`、`SKIPPED`、`INCOMPLETE`。**INCOMPLETE 不当 PASS**：超时、被结束、卡在对话框、没产出文件、等不到 gui 锁，都是「没有得出结论」。反例的 `status` 要同时满足两条才是 PASS：观察到的结局等于期望，并且原因对得上（说明里匹配 `scenarios.json` 里这条反例的 `expectDetail`），原始结局写在 `observed`。只比结局会被「没启动、没执行」空过：gui 锁等不到时 REAPER 根本没有启动，看门狗反例照样是 INCOMPLETE，却没验证到看门狗。所以结局对、原因不对，以及反例没能执行（观察到 INCOMPLETE 而期望不是它），这一行都是 INCOMPLETE（反例没能验证），不是 PASS 也不是 FAIL。每条反例必须写 `expectDetail`，缺了或不是合法正则，自测判红。整套的结局取最差的一个。退出码：0 全 PASS、1 有 FAIL、2 有 INCOMPLETE、3 整套 SKIPPED、64 被护栏拒绝或用法错误。

## 加载来源

REAPER 对同名的 VST3 包只留扫描顺序里最后的那个，而本机的两个系统 VST3 目录（`%COMMONPROGRAMFILES%\VST3`、`%LOCALAPPDATA%\Programs\Common\VST3`）里装着同名、同类 ID 的发布版。私有插件目录排在前面、或扫描缓存里留着发布版的时间戳时，系统目录里的发布版会盖掉刚复制进去的副本：渲染与对拍照样全绿，测的却是装机版。结果里的 sha256 只证明复制了哪份文件，不证明 REAPER 加载了哪份，所以工具做三件事。

1. **顺序**：`vstpath64` 里私有目录（`<CfgDir>\plugins`）排在最后，两个系统目录按上面的环境变量写法显式写在它前面（REAPER 缺系统目录时会自己补在最后，显式写了就不补）。别的目录原样保留、相对顺序不变；与私有目录是同一个目录的旧条目（大小写、结尾斜杠、正反斜杠、环境变量写法不同都算同一个）和重复项去掉；已经是这个顺序的，不改写 `reaper.ini`。
2. **扫描缓存**：REAPER 的插件缓存（`<CfgDir>\reaper-vstplugins64.ini` 的 `[vstcache]` 一节）按文件名记时间戳，同名文件里时间戳与缓存相符的那一份直接当作已经扫过的用。缓存里留着系统目录发布版的时间戳时（上一次它赢了留下的），不管 `vstpath64` 怎么排，REAPER 用的都是发布版，并且一直这样：真机上，条目是发布版的时间戳时，私有目录排在最后也加载了发布版；去掉条目后，同样的设置加载的是私有副本。所以每次复制插件时，把被测插件在缓存里的条目（含外壳插件的 `键<序号=` 子条目，键是文件名里除字母、数字、点以外的字符换成 `_`，大小写不分）去掉，让 REAPER 重新扫描它们，由私有目录排在最后来定谁赢。缓存里别的条目、别的节、文件的换行风格和非 UTF-8 的字节一概原样，没有要去掉的条目就不写文件。结果 json 的 `scanCache.removedEntries` 是去掉的行数；文件名含非 ASCII 字符的没有已知的键，不猜着删，记在 `scanCache.unkeyed`，由下面的核对兜底。只动被测插件的条目：不给别的插件填「已扫描」的空条目来挡住第三方插件的加载，那是另一件事。
3. **核对**：每次会加载插件的 REAPER 启动，每 250 ms 读一次该进程实际加载的模块（进程退出或被结束之前再读一次），记下名字是被测的两个 `.vst3` 的模块的完整路径。场景处理完后按启动逐次核对，每个被测模块要同时满足：见到过；见到的路径都是 `<CfgDir>\plugins` 里这次复制进去的那一份（完整路径相同，或文件身份相同，如硬链接）；那份文件现在的 sha256 与复制时算的相同。核不上，场景自己的 PASS 与 FAIL 一律改判 INCOMPLETE（FAIL 也改：测的可能是另一份构建，红的原因不一定在被测副本上），说明里先写加载来源没核实和原因，再附场景自己的说明；场景本来就是 INCOMPLETE 的不动，免得盖掉它自己的原因（超时、卡对话框……）。

不计入核对的启动：不带插件链的参照渲染（不加载被测插件）；gui 锁等不到、REAPER 没有启动的那次。一个场景里一次会加载插件的启动都没有被核对，同样不算证明过，改判 INCOMPLETE。

结果 json 里每个场景行的 `facts.modules` 按启动一条记下证据：启动标签、整体结论（`Proven` 才算证明）、读到模块列表的次数、每个被测模块的状态（`Private` / `Foreign` / `Changed` / `Unseen`）、实际加载的位置、复制时 sha256 的前 12 位。位置里私有目录写成 `<cfg>\plugins\…`，系统目录写成 `<CommonProgramFiles>\…`、`<LocalProfile>\…`，别处只留文件名（`<其他目录>\…`），盘符路径与含用户名的目录不进结果。

核对的坏样例都在自测里构造，不启动 REAPER：

| 情形 | 结局 |
|---|---|
| 被测模块是从系统 VST3 目录加载的同名模块（`Foreign`） | INCOMPLETE，说明里点名是哪一个 |
| 私有副本也加载过，但同名的别处模块同样加载过 | INCOMPLETE |
| 一个被测模块都没见到（`Unseen`） | INCOMPLETE |
| 路径对，但文件现在的 sha256 与复制时不同，或读不出来（`Changed`） | INCOMPLETE |
| 一次也没读到进程的模块列表（`Unreadable`） | INCOMPLETE |
| 没有被测副本的清单（`NoExpected`） | INCOMPLETE |
| 一个场景里没有一次会加载插件的启动被核对 | INCOMPLETE |
| 场景自己的结局是 FAIL | 同样 INCOMPLETE |
| 场景自己已经是 INCOMPLETE | 不动，原因保留，证据照写 |
| 多次启动里有一次核不上 | 整个场景 INCOMPLETE |
| `vstpath64` 里私有目录排在最前、只有私有目录、没有这一行、夹在系统目录中间 | 安装时改写成新顺序 |
| 扫描缓存里被测插件的条目（含外壳子条目、大小写不同的键、最后一行没有换行的） | 安装时去掉；别的条目、别的节、CRLF 与非 UTF-8 字节原样 |
| 键只是前缀相同的别的文件、别的节里同名的键 | 不动 |
| 扫描缓存里没有要去掉的条目 | 不写文件（内容与修改时间都不变） |
| 被测插件的文件名含非 ASCII 字符 | 没有已知的键，不猜着删，记进 `scanCache.unkeyed` |

## 怎么跑

REAPER 没有无头模式，需要一个真实桌面，并且占用 gui 锁（同一时刻最多一个 GUI 任务）。先用本机 gates 构建出 `dev` 风味的两个插件（构建目录里要有 `rinne-build.json` 与 `rinne_nulltest`），再：

```
pwsh scripts/reaper/doctor.ps1 -CfgDir <私有配置目录> -Init
pwsh scripts/reaper/doctor.ps1 -CfgDir <私有配置目录> -BuildDir build-wf -UserTestingMarker <标记文件路径>
pwsh scripts/reaper/run.ps1 -CfgDir <私有配置目录> -BuildDir build-wf -LogDir <结果目录> -UserTestingMarker <标记文件路径> -Repeat 5
pwsh scripts/reaper/run.ps1 -SelfTest
```

- `-CfgDir` 必须是显式的绝对路径，放在 REAPER 的默认资源目录**之外**。`doctor.ps1 -Init` 建目录、私有插件目录、最小的 `reaper.ini`（Dummy 音频设备）和哨兵文件。`-Init` 只接受还不存在的目录、空目录，或以前 `-Init` 过的目录（有哨兵，已有的 `reaper.ini` 不动）；已有内容又没有哨兵的目录一律拒绝，什么都不写，也没有绕过的开关：那多半是一份真实的 REAPER 配置（例如便携版的目录），冒烟会改它的 `reaper.ini`、往它的插件目录里复制插件。首次用空目录启动 REAPER 会扫描系统 VST3 目录，可能很慢；可以把已有的插件缓存复制进私有目录来避免。私有目录里的插件缓存含本机装了哪些插件，**永远不进仓、不进日志**。
- `-UserTestingMarker`：维护者上机测试期间放这个标记，存在时整套 SKIPPED。路径由调用方（本机包装脚本）传入。
- `-Only <id 正则>` 只跑部分场景，`-NoNegative` 不跑反例，`-Repeat N` 连跑 N 轮。
- 结果写 `<结果目录>/<时间>-<构建 sha7>.json`：每轮的耗时、结局、每个场景的结论与说明、插件文件的 sha256 前 12 位、REAPER 启动次数、默认资源目录前后核对的结果；每个场景行的 `facts.modules` 是每次启动里实际加载的被测模块的位置与核对结论，`scanCache` 是装插件时从扫描缓存里去掉了几行（见上面的「加载来源」）。结果里和控制台上的路径一律脱敏：从盘符或 UNC（反斜杠、正斜杠写法都算）起：紧跟在开引号（`"` 或 `'`）后面的路径打到对应的闭引号（闭引号后面紧跟字母或数字的是目录名里的撇号，不算；闭引号到下一个引号之间的第一个路径分隔符若不是新路径的起点，说明路径还在继续，也不算——目录名以撇号结尾的 `'C:\Work\James' Music\x'` 就是这样；认不出收尾的整段落到不带引号那一遍，宁可多打码）；不带引号的只在 `"`、换行和 `< > | ? *` 处停，空格、`'` 和全角标点都不是边界，路径后面紧跟的说明文字宁可一起打码。
- `-SelfTest` 不启动 REAPER 的主体部分在假的 APPDATA 里做；其中少量用例会用替身进程弹出几个很快消失的对话框，来验证模态框处理，期间占 gui 锁。

## 安全规则

REAPER 对不存在的 `-cfgfile` 路径不报错，而是悄悄改用默认资源目录并写它，这会改掉使用者自己的配置。所以：

1. 永不碰默认资源目录。`run.ps1` 只接受显式的 `-CfgDir`；启动前断言：路径是盘符开头的绝对路径（`\\?\` 前缀、`\\.\` 设备路径、UNC 与指回本机的 `\\localhost\C$\` 管理共享写法一律不收）；展开 `..`、解析 junction 与符号链接之后，字符串上不在 AppData 之下；再按文件身份（卷序列号加文件 ID，取自打开的目录句柄）比一遍：配置目录自己和它的每一级上级（一直查到盘符根），只要有一个与 AppData 是同一个目录就拒绝，这样 8.3 短名、大小写、尾部分隔符、subst 盘符这些字符串认不出的写法也过不去；存在却取不到文件身份（拒绝访问等）同样拒绝，证明不了就不放行；盘符所在的盘必须是本机盘：驱动器类型是 Network 的映射网络盘（字符串上它是 `Z:\…`，躲得过前缀比较）以及 NoRootDirectory、Unknown 一律拒绝，查类型出错按 Unknown，链接解析之后的真实路径所在的盘同样要查；目录存在；配置目录顶层（含隐藏条目）不得有重解析点（符号链接、junction），顶层条目列不出来也拒绝；顶层每个文件（哨兵与 `reaper.ini` 在内）的硬链接数必须是 1，大于 1 或取不到都拒绝（另一个名字可能指到使用者自己的配置；只用只读属性打开取数，不读内容）；有 `doctor.ps1 -Init` 写的哨兵文件；`reaper.ini` 存在，并且与默认资源目录里的 `reaper.ini` 按文件身份比不是同一个文件（硬链接等绕法），两边任何一个存在却取不到身份同样拒绝。任何一条不满足就拒绝启动。`doctor.ps1 -Init` 接管以前初始化过的目录时同样先查顶层链接，不会顺着链接把文件建到别处。`-cfgfile` 的实参只由一个只读常量产生，每次启动前再校验一遍。
2. 变量名不得只靠大小写区分（PowerShell 变量名不分大小写，`$c` 会盖掉 `$C`，当初就是这样让配置路径变空的）。自测会扫描 `scripts/reaper` 与 `tests/reaper` 下所有脚本：大小写碰撞、缺 `Set-StrictMode -Version Latest`、配置参数的字面量不是恰好一处且在 `Host.psm1` 里、除 `Guard.psm1` 与自测外提到 AppData，都判红。字典的 `.Keys` / `.Values` / `.Count` 遇到同名的键会返回那个条目而不是集合（扫描器自己就中过招：被扫的文件里有个叫 `$keys` 的变量，碰撞扫描就一条也报不出来），所以字典一律用 `.get_Keys()` / `.get_Values()` / `.get_Count()` 或 `GetEnumerator()`。其中脚本里把 `.Keys` / `.Values` 当属性读由自测判红；`.Count` 没有机检（List 和数组也有 `.Count`，加进判据会误伤好代码），键来自外部数据（文件名、环境变量名、配置里的 id）的字典取条目数要用 `.get_Count()`，这一条靠评审看。`.ps1`、`.psm1`、`.lua`、`.json` 里还不许夹这些不可见的控制字符：U+0000 至 U+0008、U+000B、U+000C、U+000E 至 U+001F、DEL（U+007F），以及不紧挨在 LF 前的 CR（TAB 与行尾的 CRLF 允许）：它们在编辑器和 diff 里看不见，一旦被吞掉，正则或字符串的意思就变了。
3. 看门狗只按自己启动的 PID 结束进程；对话框只处理属于这个 PID 的窗口，用户自己的 REAPER 即使开着也不会被碰。本机已有别的 `reaper.exe` 在运行时整套 SKIPPED。到点要结束进程（超时、到点、卡对话框）时，结束动作报错，或结束之后 5 秒进程还没退出，都不会当没发生：这次启动的结果带 `StillRunning`，场景 INCOMPLETE 并写明进程号和原因（结束动作的报错，或「结束之后 5 秒仍未退出」）；之后这一轮不再启动任何 REAPER，后面的场景直接 INCOMPLETE、说明写「本轮已停止」，整轮判 FAIL（`haltedBecause`）并停止后续轮次，gui 锁照常放开，也不收这个进程的探针日志（它可能还在写）。看门狗反例撞上结束不了的进程判 FAIL。
4. 音频一律走 Dummy 设备，不播放到真实声卡；启动参数固定带 `-newinst -nosplash`。
5. 模态框：「REAPER Query」（存盘提示）点「否」；渲染、插件扫描、峰值文件的进度窗放行；其余可见对话框（未选音频设备、Project Load Warning、REAPER Error、录音结束保存框、Lua 报错、评估许可的 About REAPER 提示窗等）持续半秒以上就判卡死，关窗并结束进程，场景为 INCOMPLETE。许可提示窗不会被自动点掉：评估期满后应购买许可证。未知对话框的标题进结果前先打码：盘符路径（目录名里带空格的也一样）和 UNC 路径整段换成 `<path>`，打到双引号或标题末尾为止（空格、撇号、全角标点都不是边界，单引号括起来的路径也宁可多打码）；标题末尾 REAPER 自己的 `- REAPER v…` 后缀保留，认不出的结尾宁可一起打码；截断到 40 个字符。
6. 每轮前后各取一次默认资源目录的清单（文件的大小与修改时间），变了就判红并停止后续轮次。列不出来的子目录（拒绝访问等）不会悄悄漏掉：记成 `unreadable` 项，前后任何一份里有就证明不了没变，按「默认资源目录可能被碰过」处理，同样判红并停止后续轮次，结果的 `defaultCfgDir.unreadable` 里列出是哪几项。读不了的目录下面的条目不算被删、新增或改了（另一份里它们是看不见，不是没了），一并归到「读不了」；某个目录在这一轮中途变得读不了，原因说读不了、证明不了没变，不说「默认资源目录变了」，仍判红。
7. 只复制本机构建、且风味与这一段相符（第一段 `dev`，第二段探针）的两个 VST3 进私有目录；构建清单的风味不对就 SKIPPED。预检还会校验 `rinne-build.json`：它得是合法的 JSON 对象，`sha` 得是 7 到 40 位的十六进制（它会拼进结果文件名，也证明测的是哪次构建），否则整套 SKIPPED 并写明原因。工程模板里插件的类 ID 是写死的，预检读两个插件包里的 `Contents/Resources/moduleinfo.json`，与模板比对；对不上（插件身份变了，链上会是「效果不可用」的空槽，渲染照样逐位相同）就整套 SKIPPED，先去更新 `tests/reaper/Rpp.psm1`。
8. `-Only` 写错、一个场景都没选中（或只选中了反例又给了 `-NoNegative`）是用法错误：退出码 64，不启动 REAPER，也不写结果文件；零个场景的一轮不会落成 PASS。
9. 自测里用到 subst 盘符（验证文件身份层认得出指向 AppData 的盘符）：映射对整个登录会话可见，自测被硬结束时清理不会跑。所以自测开头先清上一次留下的残留，只清同时满足两条的：盘符在 Z 到 U 之间；目标是自测临时目录（固定前缀加 32 位十六进制）。别的映射一个不碰，清了哪个字母、指向哪里只写在本机的自测输出里。

## 第二段：探针构建进真宿主

第二段让「探针构建 → REAPER → 探针日志 → `scripts/probe/analyze-probe.py`」整条链真跑一遍。先用 `scripts/build.ps1 -Probe` 构建探针风味（两个探针插件的类 ID 与正式版不同），再：

```
pwsh scripts/reaper/doctor.ps1 -CfgDir <私有配置目录> -BuildDir build-probe -UserTestingMarker <标记文件路径> -Probe [-Python <解释器路径或 PATH 上的命令名>]
pwsh scripts/reaper/run.ps1 -CfgDir <私有配置目录> -BuildDir build-probe -LogDir <结果目录> -UserTestingMarker <标记文件路径> -Probe [-Python <解释器路径或 PATH 上的命令名>]
```

- 场景在 `scenarios.json` 的 `probe` 一节，第一段的种类不能写进去，探针的种类也不能写在第一段。工程是一条轨道 `[Probe In][Probe Out]`（In 在首、Out 在末），音源是 `rinne_nulltest make-signal` 生成的测试信号，走 Dummy 设备。两端 state 里写同一个组，feedback 保持探针默认的 0，D 是默认的 100 ms。预检另查 Python 3 解释器（没给 `-Python` 就找 `py -3`；给了就可以是解释器文件的路径，也可以是 PATH 上的命令名如 `python`、`py`——不是现成的文件时按命令名在 PATH 上解析，带通配符的名字不解析，之后一律用解析出来的路径，`py` 启动器的 `-3` 也按解析后的路径判）、`analyze-probe.py` 在、文档目录取得到且列得出清单。
- 记录窗口只靠三个隐藏参数开（`auto_case`、`auto_variant`、`auto_record_s`），探针的窗口按钮 Lua 碰不到。Lua 按参数名找到它们（不假设下标），按探针规则表的首现顺序换算成整数写入，每次写完核对显示值；先写 case 与 variant，最后两端一起写记录秒数。探针自动开的窗口里 `buf` 写 `-`，`guard` 写 `na`。
- 稳态格（`probe-play`，case `CB-01`、variant `steady`）：实时播放，停走带（探针在停走带时自动 Ping 一次），等记录窗口到时，再正常退出 REAPER。不能结束进程，否则日志不收尾。导出格（`probe-export`，case `CB-04`）：同一段范围渲染两次，两次都占一次 REAPER 启动。`export-offline` 是全速离线渲染（工程的渲染速度 `RENDER_1X` 为 0），REAPER 对插件报离线模式；`export-rt` 是在线渲染（Online Render，`RENDER_1X` 为 2），按实时速度跑，对插件报实时模式。不能用 1x Offline（`RENDER_1X` 为 1）充当在线渲染：它虽然也按实时速度跑，对插件报的仍是离线模式，两次比的就不是离线与实时。两份结果用 `rinne_nulltest compare` 对拍，写成分析器认的 `compare-*.csv` 一行。
- 每格从日志里读出并判定：In、Out 各一份，各自恰好一个测试格且采样率对；正常收尾；块数够；没丢记录（丢弃计数与块序号缺口都是 0）；每一块的块长不超过它自己声明的最大块长（`B` 行逐块带 `n` 与 `n_decl`，一份日志里 prepare 可以有多次、`n_decl` 不止一个值，所以逐块比，不拿全文件的最小值或最大值去比；判红时写超出的块数与第一例），播放中恰为设定的块长；两端都配对到本进程；D 恰为 100 ms 的样本数；每个启动（稳态格一次，导出格两次，各自）的 Ping 求出的延迟恰为 D（按样本），没有 Ping 就判红；播放中的块（`playing` 为 1）的 `nonrt` 恰为这一次该有的值：稳态格与在线渲染是 0（宿主按实时调用），离线渲染是 1，同一次里不许一部分 0 一部分 1。驱动记下的几个时间（停走带到退出、渲染耗时、退出由谁定的）原样写进这一格的事实里。
- 然后对这一格的日志目录跑 `analyze-probe.py <目录> --json --redact <用户名> --redact <主机名>`，原始输出原样存下。分析器的判据按 Cubase 的清单设计，REAPER 下多数项是数据不全，这正常：每格只把 `analyzerMustPass` 里的项计入结局（稳态格 A1、A4、A8，导出格 A3、A8），其中有 FAIL 就 FAIL，没到 PASS 就 INCOMPLETE；别的项照录、打星号、不计入。A2、A5、A6、A9 在这一段没有对应的操作（反复切换、三种格式组合、改轨道名、存盘重开），A7（hostNs）取决于宿主怎么给 VST3 的系统时间，REAPER 上的结论都不外推到 Cubase。退出码 2 是分析器拒收日志，说明日志与分析器的契约对不上：这一格 INCOMPLETE，整套停下，不改探针或分析器去凑。整轮合在一起再跑一次分析器，只作记录；反例格不并进去（它故意不设组，丢记录与同键的重复记录会混进整轮的读数）。另外，分析器的 F1（Cubase 清单矩阵的覆盖）按 `(case, variant, buf, guard)` 认格，而探针自动开的窗口里 `buf` 写 `-`、`guard` 写 `na`，所以 REAPER 的日志上 F1 不会满足；这一段不看它。
- 反例 `neg-probe-unpaired`：两端不设组，必须判 FAIL，且原因里有「没有配对」。

收日志。探针不读环境变量（发布版与探针构建都一样），日志一律写在文档目录（`[Environment]::GetFolderPath('MyDocuments')`，可能在 OneDrive 下）下的 `Rinne Probe Logs`，文件名 `probe-<I|O>-<pid>-<tok4>.csv`。维护者接着要在 Cubase 里往同一个目录写上机数据，REAPER 的日志不能留在那里混进去，所以每个 REAPER 进程退出后立即把它自己的日志搬走：

1. 只认同时满足这几条的条目：直接在这个目录里（不进子目录）；是普通文件（目录、链接一律不碰，硬链接数大于 1 的也不碰）；名字恰好是上面的格式，其中 pid 写成不补零的十进制、最多十位（`probe-I-0123-…` 这样补零的名字不是探针写的）；pid 是这次启动、并且已经退出的 REAPER；修改时间落在这次启动到现在之间（早于启动的是同号的旧进程留下的，晚于现在的这次启动写不出来）。「已经退出」不只按 pid 查：Windows 会很快复用 pid，REAPER 退出后同一个 pid 可能已经分给了别的进程。所以再看现在持有这个 pid 的进程是什么时候开始的——它比这份日志最后一次写入还晚开始（留 2 s 时钟余量），就不可能是写它的那个，这是 pid 被复用，写日志的进程其实已经退出，照常搬走并在本轮结果的 `notes` 里记一笔；开始得更早（或只晚 2 s 以内）就是写它的进程还在，不动、判红；读不到开始时间（拒绝访问等）同样按还在处理，原因里写明没法排除 pid 复用。这里不拿开始时间去比「这次启动的时刻」：真正的 REAPER 恰恰是这次启动之后才开始的。

   pid 没人持有（进程已退出）时，上面这些单凭 pid 与修改时间的条件说明不了日志是谁写的：同号的别的进程（例如 Cubase 里的探针）若在窗口里写了日志、又已经退出，名字、pid、修改时间都对得上。所以文件钉住之后还要过两道只有真日志过得去的判据（都对钉住的那个对象，见第 2 条）：H 行（第 2 行）里的 `host_kind` 得是 `other`（REAPER 不是 Cubase 也不是 LUNA，探针按 `other` 写；Cubase 里的探针写 `cubase`），`role`、`pid`、`tok4` 与文件名一致，H 行读不出来（文件太短、第 2 行没写完、魔数不对、列数不对……）也不动；文件的创建时间得落在这次启动到这次启动的 REAPER 退出（runner 记下的进程退出时刻，加 2 s 余量；进程自己报的退出时刻只在落进「启动前一刻到检测到退出的当下加 1 s」时才采信——真机上偶尔读出 1601 年，那样的值取检测到退出的当下，只会把上界放宽几百毫秒）之间——pid 复用只能发生在原进程退出之后，复用者新建的文件创建时间一定晚于它，更早的进程留下的文件创建时间早于这次启动。这一道比修改时间硬：修改时间谁都能改，创建时间只有新建那一刻才定。不符的不动、判红，原因里写明是哪一条；原因里不回显文件里的内容（`host_kind` 只在属于枚举 `cubase` / `luna` / `other` 时才写出来）。这两道对所有已确认写它的进程已退出的日志都做，包括上面「pid 被复用、照常搬走」的那一种。

   NTFS 有文件名隧道：同一目录里同名文件被删或改名之后 15 s 内又以同名新建，新文件会继承旧文件的创建时间。继承只会让创建时间变早，所以对下界只会更保守（旧文件在启动之前创建，新文件继承了它，会被拒），对上界则可能放过——前提是同一个文件名刚被删过或改过名，而文件名里有这次启动的 pid 和探针随机取的 `tok4`，写出这个名字的只有这次启动的 REAPER 里的探针，它的日志在收日志之前不会被删或改名，所以这个缺口在这里够不着；而且创建时间只是几道判据之一，H 行与 pid 持有者的开始时间同样要对得上。
2. 先把原文件钉住：以只放行读的共享方式打开（带 DELETE 权限，链接按链接本身打开，不跟到目标上），钉住期间别的程序写不了、改不了名、删不了它。钉住之后大小与修改时间还得是列目录时看到的那个，创建时间与 H 行（第 2 行，开头读几百字节）也从这个钉住的句柄读，读完把位置放回开头。然后从这个钉住的流里算 sha256、复制到 `<结果目录>/<时刻>-probe-run<k>/probe-logs/<场景>/`（已有同名文件就不复制），核对复制件的 sha256 相同，最后在同一个句柄上标记删除。从读内容、算哈希到删除，中间没有别的对象能顶替它；删的只会是已经原样复制出去的那个文件（单个文件，不递归，绝不删目录）。哈希不同、进程还在、结果目录里已有同名文件、列目录之后原文件变了、被别的程序占着钉不住、硬链接、创建时间不在这次启动的存活区间里、H 行不是 REAPER 里的探针写的或读不出来，都不动（不删）并判红。
3. 每轮前后各列一次该目录的清单（名字、大小、修改时间、是否重解析点、硬链接数；子目录记 `dir`，联接记 `dir|link`），除本轮新出现的自己的文件外必须完全相同；变了一轮判 FAIL，并停止后续轮次。重解析点标记与硬链接数都进清单的值，别人的文件被换成大小、修改时间都相同的链接时，前后比较照样看得出来（硬链接数是尽力取的，一时取不到——例如 OneDrive 正在同步、杀毒软件短暂独占——记 `?`，不影响列清单）。比较时某一项前后两份里有一侧是 `?`，这一项只比前三段（大小、修改时间、重解析点），不因为「这一次没取到」判变，在本轮结果的 `notes` 里另记一笔「硬链接数没取到」（名字只写散列，控制台与结果 json 的 `linkCountUnknown` 另有个数）；前三段有变照样判变，两侧都取到才比硬链接数。「本轮自己的文件」只除外开头的清单里本来没有的名字：开头就在清单里的名字，哪怕名字像本轮的，也照常比，这样时间与 pid 的筛选万一选错，这一道照样会红。列不出清单也不跑：看不见不能当作没变。文档目录在 OneDrive 下时，别人的文件若在这一轮里恰好被按需下载或释放，重解析点标记可能跟着变（没有实测过），这一轮会判 FAIL，重跑即可。
4. 比较要看全部条目，但写出去的东西不留别人的文件名（文档目录里可能有维护者给 Cubase 写的文件）：落盘的清单和变化报告里，不是探针日志命名的条目，名字换成「每轮一把随机盐加名字」的 sha256 前 8 位（`other-<8 位十六进制>`），盐只在内存里、不落盘，换一轮散列就对不上；大小、修改时间、链接标记照写，排查时要看。探针日志命名的条目（`probe-<I|O>-<pid>-<tok4>.csv`）原样写。判 FAIL 时的原因文字（控制台、结果 json）只写变化类型（`removed` / `changed` / `added`）加散列，同一轮落盘的 `docs-listing-before.json` 与 `docs-listing-after.json` 里找得到对应的条目。

第二段的结果写 `<结果目录>/<时间>-<构建 sha7>-probe.json`；本轮目录里另有每格分析器的原始输出 `analyze-<场景>.json`、整轮那一次的 `analyze.json` 与文档目录前后的清单（别人的文件名只留散列，见上面第 4 条）。

以后再加场景（例如回声间隔），只需要往 `scenarios.json` 加条目，再在 `Scenarios.psm1` 的登记表里为新的 `kind` 加一项处理函数。条目的 `env` 字段会按原样设进 REAPER 进程的环境变量（`{work}` 换成本轮的工作目录）；探针本身不读它们。

## 常见现象

- 结果 INCOMPLETE，说明以「插件加载来源没核实」开头：先看这个场景行的 `facts.modules`。`Foreign` 是被测模块从别处加载的（系统 VST3 目录里装着同名、同类 ID 的发布版，位置写成 `<CommonProgramFiles>\…` 或 `<LocalProfile>\…`）；`Unseen` 是整次启动都没见到该模块（每 250 ms 读一次，太短的启动可能漏掉）；`Unreadable` 是一次也没读到进程的模块列表；`Changed` 是路径对但文件的 sha256 变了。工具已经把私有目录排在最后、清掉了缓存里被测插件的条目，仍是 `Foreign` 就去看 `vstpath64` 里是不是还有别的目录里有同名包。**不要**为此卸载、改名或移走系统目录里的发布版，那是只读的。
- 第一次或插件更新后启动较慢：REAPER 在重新扫描被换掉的 VST3，进度窗会被放行，超时是 90 s。
- 结果 INCOMPLETE 且说明里有「卡在对话框」：说明里列出了见到的窗口（标题里的路径已打码），按名字处理或加进 `Host.psm1` 的已知清单。
- 评估期内，许可提示窗（`license-nag`）只在部分启动时出现，同一次启动里还可能见到 REAPER 的新版本提示窗（记作 `unknown-dialog`）。碰上的那一格 INCOMPLETE，不点掉、不在本轮里重试；要结论就另跑一轮，两轮的结果都留着。
- 第二段停走带之后约 4.4 s 才有 Ping 结果：先静音一段（D 加两块再加 50 ms），再注入并回读整段测试序列，恢复干声与回送，最后等安全链 500 ms 的淡入走完。宿主在停走带之后至少要再调用插件 4.4 s，Ping 才跑得完，所以稳态格停走带后还留 6 s 多才退出 REAPER：场景表 `probe.limits.afterRenderSeconds`（现为 6.5 s）是这个时间的唯一真源，场景表校验要求稳态格的 `recordSeconds + marginSeconds - leadSeconds - playSeconds` 不少于它（把 `playSeconds` 改长到不够，校验当场判红，不等到真跑才因为没有 Ping 判 FAIL）；宿主提前不再调用或进程提前退出，日志里就没有 `ping` 事件，这一格判 FAIL。Ping 事件写进日志不受记录窗口约束：窗口关了之后才跑完的 Ping 照样记（在线那趟的 Ping 曾在窗口关闭 10 s 之后写出）。
- 导出格的渲染结束也是一次停走带，离线、在线两趟各自都要有 Ping。驱动退出 REAPER 的时刻取两者里更晚的：记录窗口结束，或渲染返回后再等 `afterRenderSeconds`（同一个字段，现为 6.5 s，由任务文件带给驱动，脚本里不写字面量）；它把这次是谁定的（`exit_bound`：`window` 或 `after_render`）和渲染返回到退出的秒数（`render_end_to_exit_s`）原样写进这一格的事实。导出格的记录窗口是 19 s，尽量盖住整段在线渲染（连同准备要 11 到 13 s，开始渲染的时刻偶尔会晚好几秒）。标准窗口下的真跑里两趟都是窗口定退出时刻：离线渲染只要 1 s 左右，渲染返回后 18 s 多才退出；在线渲染要 11 s 多，渲染返回后 8 s 多才退出。所以 6.5 s 这一项在标准窗口下不起作用，它只是窗口被改短时的下限。
- 缩短窗口的实验（3 s、6 s、9 s 的窗口各跑成一对，每对都 PASS）里，窗口先于「渲染返回后 6.5 s」结束时，两趟都是 `after_render`、恰在渲染返回后 6.500 s 退出（9 s 窗口的离线那趟是窗口定的，8.5 s），所以这一项需要时确实生效。但它不保证 Ping 一定出来：同样的实验里另有两次失败，6 s 窗口那次离线那趟没有 Ping（日志里的块计数在渲染返回后 1.7 s 就不再增长，窗口还没到），3 s 窗口那次离线那趟导出的 wav 整段静音（对拍判「A 里没有声音」）。两次都如实判 FAIL，用同样参数重跑没有再出现，原因没查清，不当成窗口长短造成的。
- 第二段的 A7（hostNs）在 REAPER 上过不了，不计入：判据要求时间戳严格递增，而 REAPER 给 VST3 的系统时间只有毫秒精度。块长 64 时相邻回调常落在同一毫秒（一轮实测 6150 次成对的播放中回调里，每端约有 4300 次的时间戳不比上一次大），Dummy 设备成批调用时块长 512 也会碰上；同一次回调里 In 与 Out 看到的时间戳偶尔还差 1 ms（块长 1024 与离线导出里见过）。两端的记录窗口各由自己的定时器打开，哪一端先开不固定。
